# Карта довіри в реальному часі по UDP

Два напрямки, обидва працюють одночасно і на різних адресах.

**Вхід.** До сервера під'єднуються і шлють кадри: глибину, позу, параметри
камери, зображення і розріджені точки VSLAM.

**Вихід.** Сервер щокадру віддає 2D карту довіри по пікселях і приріст
воксельної карти, тобто ті вокселі, які цей кадр змінив.

```
   джерело кадрів                сервер                      споживач
 (VSLAM + FDE на борту)   occupancy_3d_map.py --mode udp   (автопілот, шар безпеки)
         │                         │                              │
         │  FRAME2 :9000           │   CONF2D    :9001            │
         │  глибина, поза, K,      │   2D карта довіри            │
         │  зображення, точки ────►│   ───────────────────────────►
         │                         │   GRID_DELTA :9001           │
         │                         │   змінені вокселі ───────────►
```

## Швидкий запуск

Три термінали. Перший, споживач:

```bash
cd src && source ../.venv/bin/activate
python3 udp_conf_receiver.py --port 9001 --output_dir ../live --save_png_every 10
```

Другий, сервер:

```bash
python3 occupancy_3d_map.py --mode udp \
    --listen_port 9000 --send_host 127.0.0.1 --send_port 9001 \
    --dataset_root ../datasets/euroc/2026-04-01_12-13-18_000_quadrotor \
    --depth_refiner ../refiners/loo_euroc_zoedepth.npz --sky_cue \
    --bounds_radius 60 --voxel_resolution 1.0 --max_depth 50 \
    --output_dir ../live_map
```

`--dataset_root` тут потрібен лише для імені набору, щоб вирішити, чи
застосовувати маску гвинтів. Кадри беруться з мережі, а не з диска.

Третій, джерело. Для перевірки без апаратури воно програє записаний набір:

```bash
python3 udp_replay_sender.py \
    --dataset_root ../datasets/euroc/2026-04-01_12-13-18_000_quadrotor \
    --vslam_dir ../results/euroc/dpvo --fde_dir ../results/euroc/zoedepth \
    --host 127.0.0.1 --port 9000 --n_frames 40 --rate 10 --send_intrinsics
```

```
  ТАК  приріст воксельної карти доходить
```

Рядки зводяться **за номером кадру**, тобто видно не просто що щось летить, а
що на кадр 7 повернулась карта саме для кадру 7, і за скільки мілісекунд.
Сервер піднімається окремим процесом, тобто той самий, що в бою.

Подивитись, як виглядає чесна відмова:

```bash
python3 udp_demo.py --n_frames 6 --no_landmarks
```

Усі рядки стануть «не прийшла», а підсумок скаже, що без розріджених точок
сервер карту довіри не вигадує.

## Що зобов'язаний давати відправник

| поле | обов'язкове | без нього |
|---|---|---|
| глибина, поза, K | так | кадр відкидається |
| розріджені точки VSLAM | **так, для карти довіри** | немає калібрування, отже немає й ваг: кадр іде лише в базову карту |
| зображення, яскравість | ні | не працює вето неба, крони на горизонті губляться |

Пози і точки мають бути **в одній світовій системі та в метрах**. Сервер нічого
не вирівнює і VSLAM не запускає. Монокулярний VSLAM свого масштабу не має, тож
на борту його дає інерціальний модуль або висотомір, а в офлайновому
експерименті він береться з одноразового вирівнювання Sim(3) до еталона, і саме
це робить `udp_replay_sender.py`.

## Що означає «з урахуванням попередніх кадрів»

Три механізми, усі живуть у `realtime_map.RealtimeConfidenceMapper` і
переживають кадр.

1. **Самоналаштовні масштаби.** `residual_scale` це поточна типова похибка
   підгонки, `bandwidth_scale` це типова щільність опорних точок. Обидва
   згладжені експоненційно з періодом напівзгасання 30 оновлень. Вага довіри
   рахується відносно них, тобто відносно того, що цей політ сам про себе
   виміряв. У тесті на наборі №1 видно, як `S` сходиться від 10,1 до 7,8 м за
   перші сорок кадрів.
2. **Накопичення в логарифмі шансів.** Кожен кадр додає свідчення до того, що
   вже є у вокселі, з обмеженням від мінус 4 до 4.
3. **Вага узгодженості.** Спостереження, що суперечить накопиченому стану,
   придушується тим сильніше, чим впевненіший був той стан.

## Протокол

Заголовок спільний для всіх типів, до нього додається стиснений zlib вміст,
порізаний на шматки по 1400 байтів і зібраний на приймачі за номером
повідомлення.

| тип | номер | вміст |
|---|---|---|
| FRAME | 1 | старий кадр: глибина, поза, K. Досі приймається |
| GRID | 2 | уся сітка |
| FRAME2 | 3 | кадр з зображенням і розрідженими точками |
| CONF2D | 4 | 2D карта довіри, нечисло означає відкинутий піксель |
| GRID_DELTA | 5 | індекси змінених вокселів і їхні нові значення |

Приріст замість повної сітки це не дрібниця. Сітка 120 на 120 на 120 важить
6,9 МБ, а один кадр чіпає близько півтори тисячі вокселів, тобто 24 КБ. На
15 Гц це різниця між 104 МБ/с і 0,4 МБ/с.

2D карта довіри йде у float16, бо для величини від 0 до 1 цього досить. Кадр
640 на 480 це 614 КБ до стиснення і 259 КБ після, тобто близько 3,9 МБ/с на
15 Гц.

## Поведінка під перевантаженням

Прийом винесено в окремий потік з чергою на `--queue_frames` кадрів. Якщо
джерело швидше за обробку, **найстаріші кадри викидаються і рахуються**. Для
шару безпеки це правильна політика: застаріла карта гірша за пропущений кадр.
Без черги кадри так само губилися б, але мовчки, у буфері сокета.

Виміряно: 60 кадрів надіслано якнайшвидше, `--queue_frames 1`, оброблено 19,
відкинуто як прострочені 41, і це видно у підсумку.

кадру порівнювались з одним знімком стану, а 27 мільйонів вокселів це 108 МБ на
копію. Для локальної карти безпеки такий радіус і не потрібен.

## Обмеження

Сітка нерухома: виділяється навколо першої пози і не їде за апаратом. Якщо він
вийде за межі, точки поза сіткою просто не враховуються. Рухома локальна карта
це окрема робота.

`--voxel_resolution auto` і `--max_depth auto` у цьому режимі недоступні, бо
обидва рахуються з усієї траєкторії, якої в реальному часі ще немає. Сервер
скаже про це явно і зупиниться.

Передача без підтверджень і без повторів, як у RTP. Втрачений шматок означає
втрачене повідомлення цілком. Для телеметрії це правильний вибір, але якщо
споживач під'єднався посеред польоту, він побачить лише дальші прирости. Щоб
він наздогнав стан, є `--publish_full_grid_every N`.
